### 4. 抽取器迭代（遇到的问题）

1. **lxml 整页解析会丢内容**：`SA0541` 等页面因 `<p>`/`<font>` 未闭合、`<div>` 套在 `<p>` 里，
   libxml2 按 HTML4 规则把正文整段丢弃。→ 改为「原始字符串 + `<div>` 深度配对」定位内容块，
   绕开浏览器式解析规则。
2. **BOM/杂字符**：部分文件以 `\ufeff` + 杂字母开头，导致没有 `<body>`。→ 解析前清洗。
3. **重复内容**：新版页面同页存了繁、简两份；栏目目录页整页也是繁简双份。
   → 只取 `.trad` 块；清洗时丢弃 `class` 含 `simp` 的元素。
4. **页头/导航混入**：栏目页、著作页带搜索栏/菜单。→ 按 id（`lang-bar`、`notediv`）剥离；
   著作优先取 `#maindiv`。
5. **行内字号陷阱**：部分页面用 `<span style="font-size:20pt">` 包住整篇正文，
   若当作标题放大，整页字会变大。→ 只有文本 ≤ 40 字的元素才保留字号/颜色，
   映射为 `data-fs` / `data-c`。
6. **注释链接**：`onMouseover="note(this,N)"`、`local(this,N)`、`note_over(N)` 三种写法，
   统一转成 `class="n|l" data-n="N"`，不再依赖内联事件。

### 7. 存储形式对比（回答「数据库是不是更小」）

用同一批 7615 页正文做的实测：

| 形式 | 体积 |
|---|---|
| HTML（含标记） | 64.10 MB |
| 纯文本（去标签） | 58.23 MB |
| **SQLite（纯文本，无索引）** | **62.95 MB** |
| SQLite（每页 gzip 存 BLOB） | 21.04 MB |
| **当前方案：按栏目 JSON + gzip** | **14.38 MB** |

结论：**数据库不会更小**。SQLite 不压缩文本，存储是当前方案的 4 倍多；
即使每页单独 gzip，也因丢失跨页冗余而比现在大 46%。
数据库的优势在随机读取和查询，不在体积。当前页数（7600）和单栏目体积（最大 2 MB gzip）都很小，
整栏目一次载入内存完全可行，暂时不需要数据库。

### 10. 重复度分析（用户提出「按栏目建语料库」后的测量）

用户设想：以栏目为独立仓库，页面只存「引用」，不重复存另一侧的文本和巴利原文。

实测结果（7615 页，总文本 3036 万字）：

| 块类型 | 字数 | gzip | 占压缩体积 |
|---|---|---|---|
| 巴利原文 | 2103 万 | 4.31 MB | 33.2% |
| 南传汉译（nikaya） | 750 万 | 4.41 MB | 33.9% |
| 北传汉译（agama） | 243 万 | 1.88 MB | 14.4% |
| 著作/说明（doc） | 149 万 | 1.45 MB | 11.1% |
| 比对（cmp） | 84 万 | 0.56 MB | 4.3% |
| 旧版正文 | 51 万 | 0.39 MB | 3.0% |

「北传页（SA/MA/DA/AA）里嵌入的南传文本 + 巴利原文」：

- 1396 页有嵌入
- 南传中文 232.6 万字 + 巴利 596.2 万字 = **828.9 万字，占全部文本 27.3%**
- 折算压缩体积约 **2.6 MB**（现有数据 14.38 MB → 约 11.8 MB，省 18%）

结论：**重复确实存在，但不是 1/2，而是约 27% 的文本量、18% 的压缩体积**。
原因：巴利原文本身占 60% 文本，且绝大多数只出现一次；被重复引用的只是北传页里嵌的那部分。

重组可行性初测：1337 个含南传引用的北传页中，742 页的南传正文能由「南传独立页」逐字重组出来，
24 页部分吻合，其余受引用格式（逗号列表、节略、律藏引用）影响，需要更细的解析与逐页校验。

另：SQLite 对比（同批数据）：纯文本 62.95 MB、每页 gzip BLOB 21.04 MB、当前 JSON+gzip 14.38 MB。
数据库不会更小。

程序本身没有问题。为兼顾受限环境，回退顺序最终为：
`%LOCALAPPDATA%` → `%APPDATA%` → `%ProgramData%` → `%TEMP%` → exe 旁的 `userdata`。

### 45. MA136 正文其实被「标签不闭合」吃掉了

**原因**：

- 纯净镜像 `MA/MA136.htm` 的 div **不闭合**：`<div>` 9 个、`</div>` 8 个；
- `extract.py` 的 `find_div_end()` 按深度配对找块结尾，深度永远回不到 0，返回 `-1`
  → `<div class="agama trad">` 整块正文被判空跳过；
- 只剩相邻的 `comp` 块能配上，于是这页被当成「只有对读」；
- 源数据（简体转换稿）继承同一缺陷（18 开 / 12 闭）。

**修复**：

1. `find_div_end()` 加兜底：配不到结尾时，取「下一个结构边界」——`<div id="south">`、
   `<div class="comp"`、`<div id="east">`、`<div id="north">` 或 `</body>`；
2. 同时把 `<div class="simp">` 区域整段排除，避免把简体副本里的 `comp` 再收一遍
   （否则会抽出两个对读块）。

**验证**：

- 重新抽取后，7619 条记录里**只有 `MA/MA136.htm` 一条变化**：
  `cmp 1111` → `zh 9597 + cmp 1101`，其余零改动；
- 该页内容现为两段正文（中阿含136經 + 增壹阿含45品1經），与原站同页并列的顺序一致，
  页码归属仍是 MA.136；
- 指标：逐字一致 6545 → 6543，覆盖率 ≥95% 714 → 716。
  减少的两页是 MA136 与 AA401——它们现在都完整呈现两段并列文本，品名标注与原页边界略有差异，

### 47. 异常日志工具（构建侧，不进程序）

用户希望「有问题时能输出一份异常日志以便修正」，但不想加构建自检、也不想增加体积或打扰使用。

**做法**：新增 `工具/audit_data.py`，手动运行一次即可，输出 `验证/数据异常日志.md`。

- 检查 6 类：内容块无法配对结尾、语料键缺失、空页面、仅对读页面、
  抽取字数明显偏少（剔除简体副本后）、以及总体计数；
- **不参与运行时**，也不打进 exe：脚本约 7 KB，日志约 1.5 KB，只在仓库的 `验证/` 里；
- 当前结果：无法配对 0、键缺失 0、空页 0、仅对读 0、抽取偏少 0；

  避免把导航文字算成缺失而误报（上一版就是这里误报了 8 页）。

用法：

```bat

```
